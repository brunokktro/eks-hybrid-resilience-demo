Introdução

Demonstração de resiliência de workloads em EKS Hybrid Nodes durante cenários de desconexão de rede entre a AWS e o datacenter on-premises. Prova o requisito central da Stone para a plataforma Karavela: se a AWS cair, o datacenter não pode parar.

CenárioA Stone vai levar a Karavela (IDP baseado em Kubernetes) para os datacenters de Chicago e Atlanta. O control plane do EKS roda na região AWS; apenas os nodes rodam on-premises. A pergunta que esta demo responde: o que acontece com os workloads on-prem quando a conectividade com a AWS é perdida?

O que você vai ver

  • Workloads on-prem continuam servindo durante a desconexão (tolerations)
  • Comunicação entre nodes on-prem intacta, só o cross-cluster cai
  • Node NotReady sem afetar a LAN local (bloqueio cirúrgico do control plane)
  • Load balancer local (MetalLB) independente da AWS, análogo ao F5 do design deles
  • Limitações transparentes (provisioning na desconexão, restart de node) e mitigações
  • Cloud bursting: baseline no DC, transborda para a AWS sob carga

Arquitetura

A chave: o control plane vive na AWS; os nodes e workloads vivem no datacenter. Durante uma desconexão, os workloads locais continuam operando - só as ações que precisam do control plane (novo scheduling) ficam indisponíveis.

Três caminhos de comunicaçãoLOCAL (pod-to-pod no mesmo node), CROSS-NODE (Node 1 para Node 2, ambos on-prem via VXLAN) e CROSS-CLUSTER (cloud para on-prem, atravessa a VPN). Durante a desconexão, LOCAL e CROSS-NODE continuam; CROSS-CLUSTER cai - e isso é aceitável, porque o DC é autônomo.

Fase 0: Preparar o ambiente 2 min

Antes de qualquer coisa: confirmar em qual cluster estamos apontando. Numa rotina de várias demos, apontar para o cluster errado é o erro mais comum - sempre valide primeiro.

Listar os contextos configurados no kubeconfig

kubectl config get-contexts
A lista de clusters no kubeconfig, com um asterisco (*) no contexto atual.

Garantir o contexto do cluster da demo

Se o cluster não estiver no kubeconfig, ou para renovar as credenciais, use o update-kubeconfig. O comando define o contexto ativo automaticamente.

aws eks update-kubeconfig --name llm-vmware-hybrid --region sa-east-1

Ou trocar para um contexto já existente

kubectl config use-context arn:aws:eks:sa-east-1:923739522526:cluster/llm-vmware-hybrid

Confirmar que está no cluster certo

kubectl config current-context
O ARN do cluster llm-vmware-hybrid. A partir daqui, todos os comandos da demo vão para o cluster correto.

Fase 1: Estado atual 5 min

Mostrar o cluster: os nodes, os pods dos dois lados, e as tolerations que sustentam a resiliência.

Nodes do cluster

Destaque o hybrid node: hostname mi-xxxx, OS Ubuntu, IP on-prem (192.168.3.x).

kubectl get nodes -o wide

Pods dos dois lados

kubectl get pods -n demo-stone -o wide

As tolerations no manifesto do deployment

Este é o trecho do manifesto que sustenta a resiliência. Mostre o YAML para o cliente entender o mecanismo, não só o efeito:

tolerations:
  # Quando o node fica unreachable, o controller-manager adiciona o taint
  # node.kubernetes.io/unreachable. Sem toleration, o pod e' evictado em 300s.
  # Com toleration + tolerationSeconds, o pod sobrevive pelo tempo definido.
  - key: "node.kubernetes.io/unreachable"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 3600   # 1h no demo; producao: omitir para indefinido
  - key: "node.kubernetes.io/not-ready"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 3600
  # Cilium pode reiniciar no reconnect; tolera o taint transitorio do agent
  - key: "node.cilium.io/agent-not-ready"
    operator: "Exists"
    effect: "NoSchedule"

Confirmar que os pods em execução têm essas tolerations aplicadas

kubectl get deploy server-hybrid-1 -n demo-stone \
  -o jsonpath='{.spec.template.spec.tolerations}' | jq '.'
ExplicaçãoSem tolerations, o Kubernetes faz eviction dos pods em 300s (5min) quando o node fica unreachable. Com elas, os pods sobrevivem pelo tempo configurado, ou indefinidamente. É o que garante que o DC continue operando.

Fase 2: Testes de Load Balancer 10 min

2a. Região para Hybrid Nodes (Ingress via ALB)

ALB=$(kubectl get ingress demo-ingress -n demo-stone \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
curl -s "http://${ALB}/" | jq '{hostname, message}'
O request chega ao pod on-prem. Fluxo: internet, ALB (região), Gateway, VXLAN, pod on-prem.

2b. Hybrid Nodes para Externo (Egress)

kubectl exec -n demo-stone deploy/server-hybrid-1 -- curl -s httpbin.org/ip

2c. Load Balancer On-Premises (MetalLB VIP)

O VIP local (192.168.3.240) é o papel que o F5 exerce no design de produção da Stone.

# Da LAN on-prem (ou do proprio node):
curl -s http://192.168.3.240/ | jq '{hostname, message}'
HTTP 200 - a entrada local não depende da AWS.

Fase 3: Desconexão em estado estável 10 min

Núcleo da demo. Abra três terminais lado a lado com os logs dos clients.

# Terminal 1 - LOCAL (Node1 para Node1)
kubectl logs -n demo-stone deploy/client-hybrid -f
# Terminal 2 - CROSS-NODE (Node1 para Node2)
kubectl logs -n demo-stone deploy/client-hybrid-to-hybrid -f
# Terminal 3 - CROSS-CLUSTER (Cloud para Node1)
kubectl logs -n demo-stone deploy/client-cloud-to-hybrid -f
Logs do hybrid nodekubectl logs em pods do hybrid node pode falhar (o control plane alcança o kubelet:10250 só pela VPN). Alternativa: SSH no node, ou focar no client-cloud (kubelet cloud sempre acessível).

Injetar a falha via FIS

aws fis start-experiment \
  --experiment-template-id ${FIS_TEMPLATE_ID} \
  --region sa-east-1
Após ~40s: CROSS-CLUSTER passa a TIMEOUT, enquanto LOCAL e CROSS-NODE seguem em 200.
ExplicaçãoO datacenter continua operando de forma independente, incluindo a comunicação entre nodes on-prem. Só o link cross-cluster é afetado. É exatamente o requisito do Rogério: se a AWS cair, o DC não para.
Endpoint público vs privadoNeste lab o kubelet usa o endpoint público do EKS (via internet), então o FIS derruba só o data path - o node permanece Ready. Em produção com endpoint privado + Direct Connect, o FIS derruba os dois caminhos.

Fase 3b: NotReady + Tolerations 5 min

Para demonstrar o node NotReady sem afetar a LAN local (não desconecte a NIC - isso mataria os paths locais e não reflete o cenário real), bloqueie apenas o acesso do kubelet ao endpoint do EKS.

Resolver os IPs do endpoint (mudam - sempre re-resolver)

dig +short $(aws eks describe-cluster --name llm-vmware-hybrid \
  --region sa-east-1 --query 'cluster.endpoint' --output text | sed 's|https://||')

Bloquear no node (via SSH)

sudo iptables -I OUTPUT -d  -j DROP
sudo iptables -I OUTPUT -d  -j DROP
Node NotReady em ~60s, taint unreachable:NoExecute aplicado, pods continuam Running (tolerations), LAN local segue em 200 (LOCAL, CROSS-NODE, VIP).

Reverter

sudo iptables -D OUTPUT -d  -j DROP
sudo iptables -D OUTPUT -d  -j DROP
Node volta a Ready em ~15-20s.
ExplicaçãoBloqueamos apenas o caminho node para control plane - exatamente o que acontece quando o link com a AWS cai. O cluster vê o node como perdido, mas o datacenter continua 100% operacional.

Fase 3c: Pod crash e image cache 5 min

Ponto básico e crítico: um pod que crasha durante a desconexão reinicia? Sim - o kubelet gerencia restartPolicy localmente, sem API server, desde que a imagem esteja no cache local do containerd.

Matar o container durante a desconexão

# Via SSH no node
sudo pkill -f podinfo && echo "container morto"

Ver o restart local

curl -s -o /dev/null -w "app de volta: HTTP %{http_code}\n" \
  --max-time 5 http://192.168.3.240/healthz
HTTP 200 - o kubelet reinicia o container com a imagem do cache, sem falar com a AWS.
Requisito de produçãoDuas configurações são obrigatórias: pre-pull das imagens críticas em todos os nodes, e GC do containerd configurado para não descartar imagens (discard_unpacked_layers=false). Sem isso, um crash durante a desconexão vira indisponibilidade.

Fase 4: Desconexão durante provisioning 10 min

Ainda desconectado, tentar escalar a app.

kubectl scale deploy server-hybrid-1 -n demo-stone --replicas=4
sleep 15
kubectl get pods -n demo-stone -l location=hybrid -o wide
Os pods existentes continuam Running. Os novos ficam Pending - o scheduler não alcança o node.
Limitação conhecidaDurante a desconexão, ações do control plane (novo scheduling, HPA, rollout) ficam indisponíveis. Mas os pods existentes continuam processando. Mitigação: dimensionar as réplicas iniciais para a carga esperada (N+1 ou N+2).

Fase 5: Recovery 5 min

aws fis stop-experiment --id  --region sa-east-1
O client-cloud-to-hybrid volta a 200 sozinho (auto-heal), o node volta Ready, os pods Pending são agendados. Zero intervenção manual.
kubectl scale deploy server-hybrid-1 -n demo-stone --replicas=2

Fase 6: Cloud Bursting 10 min

Cenário de elasticidade (não resiliência): a app roda no datacenter e, sob pico, transborda para a AWS.

ComplementarBursting depende da conectividade com a AWS (oposto da resiliência). Um usa a nuvem quando ela está lá; o outro sobrevive quando ela não está.

Estado normal (roda no DC)

kubectl apply -f manifests/08-cloud-bursting.yaml
kubectl get pods -n demo-stone -l app=burst-app -o wide

Pico de carga: burst para a AWS

kubectl scale deploy burst-app -n demo-stone --replicas=12
sleep 30
kubectl get pods -n demo-stone -l app=burst-app -o wide \
  --no-headers | awk '{print $7}' | sort | uniq -c
~7 pods no DC (hybrid), ~3 transbordam para os cloud nodes. Overflow automático via nodeAffinity preferred.
ExplicaçãoA plataforma serve a carga normal no datacenter, com o custo e a latência do hardware que já existe. No pico, a capacidade transborda para a AWS automaticamente, sem reconfigurar nada.

Fim do pico: consolidar no DC

kubectl scale deploy burst-app -n demo-stone --replicas=2
kubectl rollout restart deploy/burst-app -n demo-stone
NuanceO scale-down remove pods mas não move os sobreviventes de volta (a affinity só age no scheduling). Para consolidar ativamente use rollout restart ou o Descheduler em produção.

Perguntas prováveis do cliente

PerguntaResposta curta
Storage stateful?Funciona via hostPath, local PV ou CSI de terceiros (Longhorn/Ceph/array do DC). Só EBS não (preso à AZ).
Observabilidade na desconexão?Backend local (Prometheus + ADOT dual-exporter) + crictl. Alarme NodeNotReady no CloudWatch.
Pod crash reinicia?Sim, se a imagem estiver no cache local (Fase 3c).
Desconexão maior que 12h?Pods não param. Credencial: SSM 1h, IAM Roles Anywhere até 12h. Usar IRA com durationSeconds alto.
Admission webhooks?Gotcha: failurePolicy Fail bloqueia o cluster inteiro se o webhook backend estiver no on-prem. Usar Ignore ou réplicas nos dois lados.
Chicago e Atlanta?Um cluster por DC. Se único, zone labels obrigatórias (cancela evictions na zona inteira).
