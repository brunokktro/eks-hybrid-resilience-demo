Introducao

Demonstracao de resiliencia de workloads em EKS Hybrid Nodes durante cenarios de desconexao de rede entre a AWS e o datacenter on-premises. Prova o requisito central da Stone para a plataforma Karavela: se a AWS cair, o datacenter nao pode parar.

CenarioA Stone vai levar a Karavela (IDP baseado em Kubernetes) para os datacenters de Chicago e Atlanta. O control plane do EKS roda na regiao AWS; apenas os nodes rodam on-premises. A pergunta que esta demo responde: o que acontece com os workloads on-prem quando a conectividade com a AWS e perdida?

O que voce vai ver

  • Workloads on-prem continuam servindo durante a desconexao (tolerations)
  • Comunicacao entre nodes on-prem intacta, so o cross-cluster cai
  • Node NotReady sem afetar a LAN local (bloqueio cirurgico do control plane)
  • Load balancer local (MetalLB) independente da AWS, analogo ao F5 do design deles
  • Limitacoes transparentes (provisioning na desconexao, restart de node) e mitigacoes
  • Cloud bursting: baseline no DC, transborda para a AWS sob carga

Arquitetura

A chave: o control plane vive na AWS; os nodes e workloads vivem no datacenter. Durante uma desconexao, os workloads locais continuam operando - so as acoes que precisam do control plane (novo scheduling) ficam indisponiveis.

Tres caminhos de comunicacaoLOCAL (pod-to-pod no mesmo node), CROSS-NODE (Node 1 para Node 2, ambos on-prem via VXLAN) e CROSS-CLUSTER (cloud para on-prem, atravessa a VPN). Durante a desconexao, LOCAL e CROSS-NODE continuam; CROSS-CLUSTER cai - e isso e aceitavel, porque o DC e autonomo.

Fase 1: Estado Atual 5 min

Mostrar o cluster: os nodes, os pods dos dois lados, e as tolerations que sustentam a resiliencia.

Nodes do cluster

Destaque o hybrid node: hostname mi-xxxx, OS Ubuntu, IP on-prem (192.168.3.x).

kubectl get nodes -o wide

Pods dos dois lados

kubectl get pods -n demo-stone -o wide

Tolerations que mantem os pods vivos

kubectl get deploy server-hybrid-1 -n demo-stone \
  -o jsonpath='{.spec.template.spec.tolerations}' | jq '.'
ExplicacaoSem tolerations, o Kubernetes faz eviction dos pods em 300s (5min) quando o node fica unreachable. Com elas, os pods sobrevivem pelo tempo configurado, ou indefinidamente. E o que garante que o DC continue operando.

Fase 2: Testes de Load Balancer 10 min

2a. Regiao para Hybrid Nodes (Ingress via ALB)

ALB=$(kubectl get ingress demo-ingress -n demo-stone \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
curl -s "http://${ALB}/" | jq '{hostname, message}'
O request chega ao pod on-prem. Fluxo: internet, ALB (regiao), Gateway, VXLAN, pod on-prem.

2b. Hybrid Nodes para Externo (Egress)

kubectl exec -n demo-stone deploy/server-hybrid-1 -- curl -s httpbin.org/ip

2c. Load Balancer On-Premises (MetalLB VIP)

O VIP local (192.168.3.240) e o papel que o F5 exerce no design de producao da Stone.

# Da LAN on-prem (ou do proprio node):
curl -s http://192.168.3.240/ | jq '{hostname, message}'
HTTP 200 - a entrada local nao depende da AWS.

Fase 3: Desconexao em Estado Estavel 10 min

Nucleo da demo. Abra tres terminais lado a lado com os logs dos clients.

# Terminal 1 - LOCAL (Node1 para Node1)
kubectl logs -n demo-stone deploy/client-hybrid -f
# Terminal 2 - CROSS-NODE (Node1 para Node2)
kubectl logs -n demo-stone deploy/client-hybrid-to-hybrid -f
# Terminal 3 - CROSS-CLUSTER (Cloud para Node1)
kubectl logs -n demo-stone deploy/client-cloud-to-hybrid -f
Logs do hybrid nodekubectl logs em pods do hybrid node pode falhar (control plane alcanca o kubelet:10250 so pela VPN). Alternativa: SSH no node, ou focar no client-cloud (kubelet cloud sempre acessivel).

Injetar a falha via FIS

aws fis start-experiment \
  --experiment-template-id ${FIS_TEMPLATE_ID} \
  --region sa-east-1
Apos ~40s: CROSS-CLUSTER passa a TIMEOUT, enquanto LOCAL e CROSS-NODE seguem em 200.
ExplicacaoO datacenter continua operando de forma independente, incluindo a comunicacao entre nodes on-prem. So o link cross-cluster e afetado. E exatamente o requisito do Rogerio: se a AWS cair, o DC nao para.
Endpoint publico vs privadoNeste lab o kubelet usa o endpoint publico do EKS (via internet), entao o FIS derruba so o data path - o node permanece Ready. Em producao com endpoint privado + Direct Connect, o FIS derruba os dois caminhos.

Fase 3b: NotReady + Tolerations 5 min

Para demonstrar o node NotReady sem afetar a LAN local (nao desconecte a NIC - isso mataria os paths locais e nao reflete o cenario real), bloqueie apenas o acesso do kubelet ao endpoint do EKS.

Resolver os IPs do endpoint (mudam - sempre re-resolver)

dig +short $(aws eks describe-cluster --name llm-vmware-hybrid \
  --region sa-east-1 --query 'cluster.endpoint' --output text | sed 's|https://||')

Bloquear no node (via SSH)

sudo iptables -I OUTPUT -d  -j DROP
sudo iptables -I OUTPUT -d  -j DROP
Node NotReady em ~60s, taint unreachable:NoExecute aplicado, pods continuam Running (tolerations), LAN local segue em 200 (LOCAL, CROSS-NODE, VIP).

Reverter

sudo iptables -D OUTPUT -d  -j DROP
sudo iptables -D OUTPUT -d  -j DROP
Node volta a Ready em ~15-20s.
ExplicacaoBloqueamos apenas o caminho node para control plane - exatamente o que acontece quando o link com a AWS cai. O cluster ve o node como perdido, mas o datacenter continua 100% operacional.

Fase 3c: Pod Crash e Image Cache 5 min

Ponto basico e critico: um pod que crasha durante a desconexao reinicia? Sim - o kubelet gerencia restartPolicy localmente, sem API server, desde que a imagem esteja no cache local do containerd.

Matar o container durante a desconexao

# Via SSH no node
sudo pkill -f podinfo && echo "container morto"

Ver o restart local

curl -s -o /dev/null -w "app de volta: HTTP %{http_code}\n" \
  --max-time 5 http://192.168.3.240/healthz
HTTP 200 - o kubelet reinicia o container com a imagem do cache, sem falar com a AWS.
Requisito de producaoDuas configuracoes sao obrigatorias: pre-pull das imagens criticas em todos os nodes, e GC do containerd configurado para nao descartar imagens (discard_unpacked_layers=false). Sem isso, um crash durante desconexao vira indisponibilidade.

Fase 4: Desconexao Durante Provisioning 10 min

Ainda desconectado, tentar escalar a app.

kubectl scale deploy server-hybrid-1 -n demo-stone --replicas=4
sleep 15
kubectl get pods -n demo-stone -l location=hybrid -o wide
Os pods existentes continuam Running. Os novos ficam Pending - o scheduler nao alcanca o node.
Limitacao conhecidaDurante a desconexao, acoes do control plane (novo scheduling, HPA, rollout) ficam indisponiveis. MAS os pods existentes continuam processando. Mitigacao: dimensionar as replicas iniciais para a carga esperada (N+1 ou N+2).

Fase 5: Recovery 5 min

aws fis stop-experiment --id  --region sa-east-1
O client-cloud-to-hybrid volta a 200 sozinho (auto-heal), o node volta Ready, os pods Pending sao agendados. Zero intervencao manual.
kubectl scale deploy server-hybrid-1 -n demo-stone --replicas=2

Fase 6: Cloud Bursting 10 min

Cenario de elasticidade (nao resiliencia): a app roda no datacenter e, sob pico, transborda para a AWS.

ComplementarBursting DEPENDE da conectividade com a AWS (oposto da resiliencia). Um usa a nuvem quando ela esta la; o outro sobrevive quando ela nao esta.

Estado normal (roda no DC)

kubectl apply -f manifests/08-cloud-bursting.yaml
kubectl get pods -n demo-stone -l app=burst-app -o wide

Pico de carga: burst para a AWS

kubectl scale deploy burst-app -n demo-stone --replicas=12
sleep 30
kubectl get pods -n demo-stone -l app=burst-app -o wide \
  --no-headers | awk '{print $7}' | sort | uniq -c
~7 pods no DC (hybrid), ~3 transbordam para os cloud nodes. Overflow automatico via nodeAffinity preferred.
ExplicacaoA plataforma serve a carga normal no datacenter, com o custo e a latencia do hardware que ja existe. No pico, a capacidade transborda para a AWS automaticamente, sem reconfigurar nada.

Fim do pico: consolidar no DC

kubectl scale deploy burst-app -n demo-stone --replicas=2
kubectl rollout restart deploy/burst-app -n demo-stone
NuanceO scale-down remove pods mas nao move os sobreviventes de volta (affinity so age no scheduling). Para consolidar ativamente use rollout restart ou o Descheduler em producao.

Perguntas Provaveis do Cliente

PerguntaResposta curta
Storage stateful?Funciona via hostPath, local PV ou CSI de terceiros (Longhorn/Ceph/array do DC). So EBS nao (preso a AZ).
Observabilidade na desconexao?Backend local (Prometheus + ADOT dual-exporter) + crictl. Alarme NodeNotReady no CloudWatch.
Pod crash reinicia?Sim, se a imagem estiver no cache local (Fase 3c).
Desconexao maior que 12h?Pods nao param. Credencial: SSM 1h, IAM Roles Anywhere ate 12h. Usar IRA com durationSeconds alto.
Admission webhooks?Gotcha: failurePolicy Fail bloqueia o cluster inteiro se o webhook backend estiver no on-prem. Usar Ignore ou replicas nos dois lados.
Chicago e Atlanta?Um cluster por DC. Se unico, zone labels obrigatorias (cancela evictions na zona inteira).
